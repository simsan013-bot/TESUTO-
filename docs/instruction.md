# スカッと系YouTube制作 自動化組織システム — Claude Code 実装指示書

## 0. このドキュメントの目的

これはClaude Codeに「会社」を実装させるための設計指示書である。
人間（Sim）は最終承認者・例外処理担当として残り、それ以外の進行は全てエージェントが担う。

**今回のスコープ：既存チャンネル1本の運用自動化のみ。複数チャンネル対応は構造として備えるが、実装はしない。**

---

## 1. 会社としての構造（組織図）

```
Sim（代表・最終承認者）
  │
  ├─ プロデューサー（全体統括AI）
  │    パイプライン全体の進行管理。各GAS Appの呼び出し、
  │    状態管理、ゲート（Sim確認ポイント）への引き上げ、
  │    チェッカーNG時のリトライ制御を行う。
  │    人間組織における「制作プロデューサー」に相当。
  │
  ├─ ディレクター（チャンネル担当AI）★1チャンネル=1ディレクター
  │    そのチャンネルの企画方針・トーンを管理。
  │    シナリオAppへの指示出し、アナリストFBの採否判断、
  │    台本化のGO/NG判断を行う。
  │    将来複数チャンネルになった場合、ディレクターを
  │    チャンネル数分インスタンス化する前提で設計する。
  │
  ├─ アナリスト（ペルソナ群、5〜6体）
  │    シナリオApp出力後にのみ介入。
  │    視聴者ペルソナとしてフィードバックを行う。
  │
  └─ チェッカー（①〜⑦、プロデューサー直下）
       各工程の出力物をOK/NG判定する。
       ①台本品質　②キャラ別台本　③音声
       ④猫感想コメンタリー　⑤画像・アニメ素材
       ⑥動画プレビュー　⑦サムネ
       NG時：修正指示を出し再実行→最大2回リトライ
       　　　3回目もNGならSim確認ゲートに上げる
```

### 役職とパイプライン工程の対応関係

1役職が複数工程を横断する設計（1役職=1工程ではない）。

| 役職 | 担当範囲 |
|---|---|
| プロデューサー | 全工程（オーケストレーション） |
| ディレクター | scenario工程の方針決定のみ |
| アナリスト | シナリオApp出力直後のみ |
| チェッカー①〜⑦ | 各工程の出力直後、工程ごとに1体 |
| Sim | ゲートA/B/C + チェッカー3回目NG時 |

## 3. データ構造（GASスプレッドシート設計）

既存の「全体管理シート」（人間ワーカー用、6工程×着手者/着手日/完了/完了日）は**そのまま残す**（外注運用と並走するため廃止しない）。

AI自動化パイプライン専用に**新規シート「自動化キューシート」を1本作成**する。これがエージェント間の唯一の受け渡し場所になる。

### 自動化キューシート 列構成

| 列 | 項目 |
|---|---|
| A | 作品No |
| B | タイトル |
| C | チャンネルID（将来の複数チャンネル対応のため今から入れる。現在は固定値1種） |
| D | フォルダID |
| E | 全体ステータス（進行中/ゲート待ち/完了/エラー停止） |
| F | 現在の工程 |
| G | 現在のゲート（A/B/C/なし） |

以降、工程ごとに4列セット：`{工程名}_状態` / `{工程名}_出力ID` / `{工程名}_更新時刻` / `{工程名}_リトライ回数`

対象工程：シナリオ / 圧縮 / アナリストFB / キャラ別台本 / 音声 / 猫感想 / 画像 / 編集 / サムネ / 投稿

状態値は全工程共通：`待機` / `実行中` / `チェック中` / `NG_リトライ中` / `Sim確認待ち` / `完了` / `エラー`

## 3.5 チェッカーNGログ（初期チューニング用・必須実装）

初期運用フェーズ（最初の10〜20本）はチェッカーのNG率を下げる調整が最優先課題になる。
そのため、NG発生時は必ず以下を記録する専用ログを実装する。

### NGログシート 列構成（自動化キューシートとは別タブ/別シートで管理）

| 列 | 項目 |
|---|---|
| A | 作品No |
| B | チェッカー名（①〜⑦） |
| C | 試行回数（1回目/2回目/3回目=Sim確認） |
| D | NG判定理由（チェッカーが出した具体的な指摘内容） |
| E | 生成側に渡した修正指示 |
| F | 再生成後の結果（OK/NG） |
| G | タイムスタンプ |

### 運用ルール

- 全チェッカーのNG判定時、判定理由を**漠然とした一言ではなく具体的に**ログへ記録する（後で傾向分析に使うため、「NG」だけでなく「説明口調が3箇所」「文字数が目標の70%」等の粒度で残す）
- リトライ時に生成側へ渡す修正指示は、NG理由をそのまま反映させる（リトライ1回目→2回目で同じ指摘を繰り返さないよう、指示文を強化する）
- 最初の10〜20本終了時点で、NGログを集計し「どのチェッカーで・どの理由のNGが多いか」を確認する
- 傾向が見えたら、**チェッカーのプロンプトを直すより先に、生成側プロンプトに該当の注意点を先回りで埋め込む**ことを優先する（NGをチェッカーで弾くより生成時点で防ぐ方がコスト効率が良いため）
- このログは将来の複数チャンネル展開時にも共通で使う想定とし、チャンネルIDで絞り込めるようA列の隣に紐づけておくこと

## 4. 実装スコープ（今回やること／やらないこと）

### やる（v1スコープ）
- 既存チャンネル1本のみを対象に、自動化キューシートを新設
- プロデューサー・ディレクター・チェッカー①〜⑦を実装（プロンプト＋呼び出しロジック）
- 既存App（シナリオApp、圧縮ツール、キャラ別台本、Fish Audio、PRP生成、画像生成App）は**プロンプト変更せず、呼び出し方のみ自動化**
- 新規3App（編集ツール、サムネイルApp、YouTube投稿App）は最小実装でまず動かす
- ゲートA/B/C、チェッカー2回リトライ→3回目Sim確認のロジック実装

### やらない（今回は対象外）
- 複数チャンネル運用の実装（`channels/ch_a/config.yaml`構造は**設計として用意するが中身は1チャンネル分のみ**）
- 既存App群のプロンプト改修（神聖なプロンプトは触らない）
- 会計・コスト集計機能
- 既存の人間外注ワーカー向けフロー（管理者入力App等）の変更

## 5. チャンネル固有設定の構造（複数チャンネル化を見据えた布石）

```
channels/
└── ch_existing/          ← 既存チャンネル（今回はこの1つのみ作成）
    ├── config.yaml        ← トーン・ターゲット・NGワード
    ├── rules.md           ← チャンネル固有ルール
    └── tools.yaml         ← 猫感想Appなどチャンネル固有ツールの登録
```

将来2チャンネル目を追加する際は `ch_existing/` をコピーして設定を書き換えるだけで済む構造にする。**今回はこのフォルダを1つ作るだけで、複数チャンネル分岐ロジックの実装はしない。**

## 6. NG時のリトライ仕様（全チェッカー共通）

```
チェッカーがNG判定
  → 1回目：修正指示を出し再実行
  → 2回目：修正指示を出し再実行
  → 3回目もNG → Sim確認ゲートに自動エスカレーション
     （自動化キューシートのステータスを「Sim確認待ち」に変更、
      エラー内容・リトライ履歴を記録）
```

## 7. Claude Codeへの実装依頼順序（推奨）

1. 自動化キューシートの作成（GAS関数：行追加/状態更新/読み取り）
2. プロデューサーのオーケストレーションロジック（状態を見て次工程を判定・呼び出す）
3. 既存App群をHTTP POSTで呼べる形に整える（プロンプトは無改修、呼び出しインターフェースのみ追加）
4. チェッカー①〜⑦の実装（リトライ・エスカレーションロジック共通化、NGログシートへの記録を含む）
5. ディレクター・アナリストの実装（scenario工程のみ）
6. 新規3App（編集ツール／サムネイルApp／YouTube投稿App）の最小実装
7. ゲートA/B/C（Sim確認）のUI・通知
8. channels/ch_existing/ の設定ファイル作成

## 8. 申し送り事項（過去の設計原則・必ず守ること）

- コンテンツ生成プロンプト（システムプロンプト・生成ルール）は神聖。構造変更のみ許可、文面変更禁止
- GAS V8互換のため `var`/`function`使用、`const`/`let`/アロー関数は避ける
- APIキーはScript Propertiesに保存、ハードコード禁止
- `===SPLIT===`等、`=`始まりの文字列はスプレッドシートで数式誤認される。書き込み時は先頭スペース付与、GAS側比較時は`.trim()`必須
- `onEdit`トリガーは対象スプレッドシート自身のスクリプトエディタに設置（WebApp側ではない）
- コピーしたGASスプレッドシートはOAuthトークンを引き継がない。`authDrive()`等のDrive権限強制取得関数が必要
- 部分パッチでのGAS編集は構文エラーを招きやすい。ファイル全体の書き直しを基本とする
